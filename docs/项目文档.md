## 一、一句话说明

> 一个跑在**阿里云 ECS** 上的 **QQ 群聊 AI 机器人**，用 **QQ 官方机器人 API v2**，
> **零第三方依赖**（只要 Node 22+），人设是傲娇鲸鱼娘「**蓝色大肥鱼**」。

**和框架派的区别**：这不是 AstrBot / NoneBot，是**从零手写**的完整链路 ——
**鉴权 → 长连接 → 事件分发 → 分层决策 → 模型调用 → 限流 → 发送 → 容错**。

**它是什么**：在 QQ 群里像一个**有性格的群成员**那样聊天，而不是一个"问答接口"。

| 特点 | 说明 |
|---|---|
| **拟人** | 甜系傲娇的「鲸鱼娘」人设，会吐槽、会得意、会用括号写动作 |
| **有分寸** | 不该说话时**真的沉默** —— 别人互相 @，机器人不抢答 |
| **能干活** | 暗号 `ovo` 可切换「精准回答」模式，给步骤、给代码 |
| **记得住** | 最近 30 条 / 10 分钟内的上下文；冷场后自动忘记旧话题 |
| **花钱有上限** | 每天 ¥3、总计 ¥10，超了自己在群里喊"没钱了" |
| **可观测** | 自带手机可看的日志网页（额度 / 最近消息 / 实时日志） |

**你的电脑关机它也活着。**

### 2.2 QQ 服务范围限制（决定它能进哪些群）

**官方原文**（[QQ Bot 介绍与接入指南](https://bot.q.qq.com/wiki/bot_new_product-intro/)）：

| 认证状态 | 能进哪些群 | 群数上限 |
|---|---|---|
| **未认证** | **仅管理员使用，只能加到「管理员作为群主」的群** | — |
| **个人认证** | 文档说"可公开使用，500 群" | 文档写 500 |
| **企业认证** | 场景均可设为公开使用 | 更多 |

**实测（2026-09）**：即便**已认证（个人）**，q.qq.com →「服务范围」页面仍提示
「该能力正在对于企业开发者灰度，个人认证开发者敬请期待」——
「允许被添加到任意群聊」「好友（私聊）」「频道」三个开关**都不可用**。

> ⚠️ **结论：认证状态 ≠ 能力开放。** 只有问官方客服才能确认何时开放。

**两个不受限的通道**：

| 通道 | 说明 | 上限 |
|---|---|---|
| **内部体验号码** | 配置后**不受服务范围影响**，可测试对话 | **20 个号码** |
| **单聊** | 用户直接和机器人对话 | 不受进群限制 |

> 💡 **想绕过"未认证不能进别人群"**：把对方 QQ 号加进「内部体验号码」，
> 他们就能和机器人**单聊测试**，不需要拉群。**受限的是"进群"，不是"对话"。**

### 2.2.1 🔴 「机器人只能看到 @ 消息」的真正开关（2026-09-22 查明）

**症状**：机器人在某些群里**只有被 @ 才回**，另一些群里不 @ 也回。查配置、查代码都没问题。

**原因**：这是 **QQ 客户端里的一个「群级」开关**，不在 q.qq.com 后台，**普通管理员也改不了**：

```
手机 QQ → 打开那个群 → 右上角「≡」群设置 → 群机器人 / 机器人管理
        → 选中「蓝色大肥鱼」
        → 「机器人可获取的群聊消息范围」=  【获取群内全部消息】   ← 关键
        → 「机器人主动在群聊内发言」     =  打开（发卡片/视频要靠它）
```

**只有群主能改**（管理员不行）。改完 QQ 会往群里推一条系统消息：
「群主已授权蓝色大肥鱼查看群内全部对话」—— **看到这条就说明生效了**。

| 这个开关 | 机器人收到什么事件 | 效果 |
|---|---|---|
| 只接收 @ 消息（默认） | 只有 `GROUP_AT_MESSAGE_CREATE` | 不 @ 就不理 |
| **获取群内全部消息** | 还有 `GROUP_MESSAGE_CREATE` | 不 @ 也理（本项目的设计前提） |

> ⚠️ **和「服务范围」是两码事**，别混：
> · 「服务范围」决定机器人**能不能被拉进群**（见 2.2，个人认证暂时关着）
> · 这个开关决定**进了群之后能不能看到全部消息**
>
> 📌 实测（2026-09-22，本机器人自己加过的 7 个群）：
> 有的群是"全量"、有的是"仅 @"，**和加群时间、谁加的都没关系**，
> 就是群主有没有点过那个开关。**要"不 @ 也回"，就得找群主点一下。**

参考：[mai-mai 适配器文档](https://docs.mai-mai.org/manual/adapters/qq-official)、
[AstrBot 文档](https://docs.astrbot.app/platform/qqofficial/websockets.html)

### 2.3 模型计费（DeepSeek）

计价单位：元 / 百万 token。

| | 输入（缓存命中） | 输入（未命中） | 输出 |
|---|---|---|---|
| **空闲时段** | 0.02 | **1** | **4** |
| 高峰时段 | 0.04 | 2 | 8 |

> **空闲 = 除「周一至周五 9:00-12:00、14:00-18:00」外的所有时间** ——
> 群里活跃的晚上和周末都是半价。

**DeepSeek 只认两个模型名**（接口实测）：`deepseek-flash`、`deepseek-v4-pro`。
配错了会直接报 `HTTP 400 The supported API model names are deepseek-flash, deepseek-v4-pro`。

**实测成本**：约 ¥0.19 / 150 次调用，活跃群约 **¥1~3/月**（计价**保守取高峰价 + 缓存未命中**，所以实际只会更少）。

### 4.3 ⭐ 核心设计原则：能不用模型解决的，就不用模型

| 层 | 做什么 | 成本 |
|---|---|---|
| **L0 硬规则** | 长度 / 冷却 / @判定 / 静默时段 / 非文本过滤 —— **全是字符串与正则判断** | **零成本** |
| **L1 判断** | 只有真正需要语义的才交给它（"这句话是不是在跟我说话"） | 一次小调用 |
| **L2 生成** | 只负责"怎么说"（人设 + 上下文 + 分段） | 一次调用 |

**判断 max_tokens ≥ 256、生成 max_tokens ≥ 800**（太小会导致回复为空）。

### 4.4 官方接口速查（已逐条核对官方文档）

| 用途 | 方法与地址 |
|---|---|
| 拿 token | `POST https://api.bot.qq.com/app/getAppAccessToken`，body `{appId, clientSecret}` → `{access_token, expires_in:"7200"}` |
| 鉴权头 | `Authorization: QQBot {ACCESS_TOKEN}` |
| 拿网关 | `GET https://api.bot.qq.com/gateway` → `{"url":"wss://api.bot.qq.com/websocket/"}` |

| 单聊事件 | `C2C_MESSAGE_CREATE` |

| 项目 | 结论 |
|---|---|
| 接口域名 / 路径 | ✅ 与官方一致 |
| 鉴权头格式 | ✅ |
| intent 值 `1 << 25` | ✅ |

### 4.5 两条最容易忽略的官方原话

1. **`GROUP_AT_MESSAGE_CREATE` 的 `content`「已去除 @机器人的前缀」，`mentions`「不含 @机器人自身」**
   → 所以**判断"是否被 @"只能看事件名**，不能看字段。
2. **「为确保消息可达，相同 `msg_id` 可能重复推送，开发者需结合 `msg_seq` 做去重」**
   → 所以**必须去重**，否则同一句话会回好几遍。

| 项 | 设定 |

> 💡 身份标注是**每次生成时由代码加的**（`【主人（群主）】` / `【普通群员】`），

### 6.2 ⭐ 习惯动作与括号规则

**括号怎么用**：

| 规则 | 值 |
|---|---|
| **格式** | **半角括号** `(尾鳍啪地甩过来)` —— 比全角少占视觉空间 |
| **位置** | 句首或句末 |
| **数量** | **一条消息最多 1 个** |
| **时机** | **只在情绪明显时**（生气 / 得意 / 害羞 / 无语） |
| **普通闲聊** | **纯文字，不用括号** |
| **禁止** | `(歪头)(眨眨眼)` 这类**通用萌系套路** —— 要具体、贴合鲸鱼娘 |

**生气时的可选动作（这是解决"只有尾鳍拍你"的关键）**：

```
甩尾鳍 · 翻白眼 · 冷笑 · 记仇 · 假装没听见 · 威胁游走
```

**得意时**：尾巴摆摆 / "嗯，我知道" / 嘴硬不承认高兴

> ⚠️ **设计意图**：以前提示词只写"被提就炸毛"，示例里只有 1 条（尾鳍拍你），
> 所以反复挑衅**永远得到同一句**。现在提示词列出 **6 种生气方式**，
> 示例给 3 个变体，再加反重复机制兜底。

**⭐ 反重复机制（代码层）** —— 光加示例不够，模型可能"锁定"其中一个说法：

```
它最近说过的 5 句话会被回灌进提示词 → 明确要求"不要再重复同样的说法和梗"
```

| 参数 | 值 |
|---|---|
| `antiRepeat.enabled` | `true` |
| `historySize` | **5 条** |
| 作用范围 | **每个群各记各的**（不同群互不干扰） |
| 自动清理 | 超过 30 分钟的记录丢弃 |

**用户看到的效果**：反复挑衅它，它会**换着方式**回应，不会一直同一句。

### 6.3 ⭐ 什么时候会说话（最重要的部分）

**决策流程（从上到下，命中就停）**：

```
收到群消息
   ↓
① 是机器人自己发的？ → 忽略
② 只 @ 了它、没写内容？ → 回一句固定应答（咋了/在/说吧…）
③ @ 了群里别人？ → 沉默（不抢答）
④ 被 @ 了（is_you=true）？ → 一定回复
⑤ 提到关键词（大肥鱼/蓝鲸/鲸鱼…）？ → 50% 概率回复，且引用那条消息
⑥ 以上都不是 → 沉默
```

**完整行为表**：

| 场景 | 会回吗 | 概率 | 带引用 | 说明 |
|---|---|---|---|---|
| **@它 + 有内容** | ✅ 一定回 | 100% | ❌ | 点名了，必答（`is_you=true`） |
| **@它 + 没写字** | ✅ 回「咋了」这类 | 100% | ❌ | 被点名该吱一声 |
| **@别人 + 内容没提它** | ❌ **不抢答** | 0% | — | 你在跟别人说话 |
| **@别人 + 内容提到关键词** | ⚠️ 仍会回 | **50%** | ✅ **引用原消息** | 见下方说明 |
| **没 @人 + 提到关键词** | ⚠️ 看运气 | **50%** | ✅ **引用原消息** | 接话茬，引用让对象明确 |
| **没 @人 + 没关键词** | ❌ **一定不回** | **0%** | — | 原为 5% 抽样，**已关闭** |
| **私聊** | ✅ 一定回 | 100% | ❌ | 专门找它说话 |

> ⚠️ **一处容易误解的地方**：如果消息 **@ 了别人、但内容里提到了它的名字**
> （例：「@小明 蓝色大肥鱼刚才说啥了」），它**仍会按关键词路径回复**。
>
> 这是**故意的** —— 那句话确实在说它，该接。
> 但如果你希望"只要 @ 了别人就绝对沉默"，可以改成硬拦。

**关键词清单（只有"机器人的名字/别名"，不含通用词）**：

```
蓝色大肥鱼 · 大肥鱼 · 肥鱼 · 鲸少女 · 小蓝鲸 · 蓝鲸 · 鲸鱼 · 嘉然
```

> 💡 `嘉然` 是早期后台昵称留下的，留着无害。
> ⚠️ 曾经有过 `蓝色` 这个通用词，**已删除** —— 群里说「这个蓝色好看吗」不该触发它。

**只 @ 它没内容时的应答**：`policy.mentionOnlyReplies`（「咋了」「在」「说吧」这类）。

### 6.4 "刹车"清单

即使上面判定"该回"，**这几条也可能让它闭嘴**：

| # | 刹车 | 值 | 说明 |
|---|---|---|---|
| ~~1~~ | ~~**静默时段**~~ | ~~北京时间 2:00~7:00~~ | ⚠️ **已关闭**（2026-09-21）—— 用户判定：半夜本来没几个人，静默反而让偶尔来的人以为"它坏了"。想开回来：`policy.quietHoursEnabled: true` |
| **2** | **逐人冷却** | **60 秒** | 同一个人在群里 60 秒内只回一次 |
| **3** | **连续上限** | 3 分钟内最多 **2 次** | 防止它在群里连刷 |
| **4** | **最短长度** | **4 个字** | 短于这个的消息不理（**被 @ 时不受此限**） |
| **5** | **调用次数** | **800 次/天** | 超了当天沉默，第二天北京时间 0 点重置。⚠️ **这是"次数"不是"钱"** —— 别和 ¥3/天 那个话费上限搞混（2026-09-21 就因为这个误会排查了半天） |

> ⭐ **被 @ 时会绕过冷却和连续上限** —— 点名了就一定应。
> 但**日额度绕不过**（那是钱包底线）。主人也不受冷却、连续上限、抽样约束。

### 6.5 ⭐ 助手模式：用暗号 `ovo` 切换精准回答

**设计目的**：平时保持拟人的"人味"，但**需要准确答案时**能切到助手模式。

**和"主人"机制的区别**：

| | 主人机制 | **暗号机制** |
|---|---|---|
| 按什么分 | **身份**（谁在说话） | **消息**（这条消息） |
| 怎么切换 | 改配置、重启 | **打字加个前缀** |
| 谁能用 | 只有主人 | **任何人**（包括主人） |

**同一个人可以随时切换** —— 这是暗号比身份更灵活的地方。

**怎么用**：

```
群友: ovo 帮我解释一下什么是递归        →  助手模式（精准回答）
群友: ovo 我服务器 nginx 502 了怎么排查  →  助手模式（给步骤和命令）
群友: ovo                               →  普通模式（只有暗号 ≈ 没说话）
群友: 蓝色大肥鱼你好                     →  普通模式（拟人）
群友: @蓝色大肥鱼 ovo 解释下量子纠缠     →  助手模式（先剥 @ 再认暗号）
```

**触发规则（三条同时满足）**：

| # | 规则 | 例子 |
|---|---|---|
| ① | **以暗号开头**（先剥掉 `@它` 再判断） | `ovo 问题` ✅ / `你好 ovo` ❌ |
| ② | **暗号后还有内容** | `ovo` ❌（只有暗号，等于没说话） |
| ③ | 有内容时，**暗号会被去掉**再交给它 | `ovo 帮我看看` → 它看到的是 `帮我看看` |

**大小写不敏感**（`OVO` / `Ovo` 都认）。

**边界也守住了**（这些**不会**误触发）：

```
ovoid 这不是暗号     ❌ 相似词
ovovovo             ❌ 重复暗号
ovoabc              ❌ 暗号后直接接英文
ovo帮我看看          ✅ 暗号后直接接中文（这个认）
ovo，帮我看看        ✅ 暗号后接标点
```

**助手模式下有什么不同**：

| 项 | 普通模式 | **助手模式** |
|---|---|---|
| **人设/语气** | 傲娇、有情绪 | ✅ **保留**（还是蓝色大肥鱼） |
| **内容要求** | 短、口语 | **准确、完整、可执行** |
| **不确定时** | — | **必须说不确定，禁止编造** |
| **分段** | 超 40 字拆最多 4 条 | ❌ **不分段**（拆开会切断答案） |
| **反重复** | 注入"最近说过的话" | ❌ **不注入**（为换说法改写会损害准确性） |
| **引用** | 关键词触发时引用 | ❌ 不引用 |
| **冷却/抽样/长度限制** | 生效 | ❌ **全部绕过**（明确要求准确答案，不该被省钱逻辑拦） |
| **L1 判断 + 抽签** | 生效 | ❌ **跳过**（否则 L1 看不到 `ovo`，按闲聊打分拒绝） |
| **日额度** | 生效 | ✅ **仍然生效**（钱包底线） |

**实际效果对比（同一问题）**：

「递归是什么，举个例子」

```
拟人模式:  就是你把自己叫进去，然后它又把你叫进去……一直叫到有个家伙喊停，
          不然就无限套娃，最后栈炸了
          ← 生动、好懂，但没有可执行信息

助手模式:  递归就是函数自己调用自己。比如算阶乘：
          def fact(n):
              if n == 1: return 1
              return n * fact(n - 1)
          fact(5) 会一路展开成 5*4*3*2*1。关键是得有个终止条件...
          ← 定义 + 代码 + 要点
```

「我服务器上 nginx 502 了，怎么排查」

```
助手模式:  又是我……行吧。502 一般是 nginx 连不上后端的锅，按这个顺序查：
          1. ps aux | grep 你的服务名     （后端还活着吗）
          2. ss -lntp | grep 端口          （监听端口对不对）
          3. curl -v http://127.0.0.1:端口/（绕过 nginx 打后端）
          4. tail -f /var/log/nginx/error.log
             refused = 后端没起来或端口错 / timeout = 后端卡死或防火墙
          5. getenforce + setsebool        （SELinux 拦截）
          6. nginx -t 再 reload
          大概率是后端挂了或者端口写错。日志贴出来我帮你看。
          ← 6 步、带命令、带判读标准，① 开头还保留了"又是我……行吧"的傲娇
```

> 💡 **注意最后那条**：助手模式下它**依然是"蓝色大肥鱼"** —— 开头吐槽、结尾主动说"日志贴出来我帮你看"。
> **这就是"保持拟人风格 + 精准回答"同时成立的样子。**

**⚠️ 助手模式的两条关键规则（都是踩坑后补的）**：

**① 显式覆盖身份规则**

人设里「普通群员不执行指令」比助手模式的要求**更具体**，模型会照它执行。

**实测 bug（2026-09-16）**：普通群员发「`ovo写一篇50字短文`」→ 它回「**不写，你又不是我主人**」。

修法两层：
- `systemNote` 里**点名推翻**（"这条在助手模式下暂停"）
- **`stripRoleLabel: true`** —— 助手模式下**去掉【主人】/【普通群员】标注**，从源头消除冲突（比反复叮嘱可靠）

**② 必须禁止拿"懒"当理由**

**实测 bug**：主人发 `ovo写一篇50字短文` → 回「**不写。五十字也是字，懒得动**」。

根因：人设里有"聪明但**懒**"，助手模式没明确说"懒不构成拒绝理由"，模型就用它推脱。

**修完实测**：

```
普通群员 ovo助手模式 → ✅ 五十个字？行吧。「海面浮着碎月光，一条鲸慢悠悠游过…」
普通群员 普通模式   → ❌ 不写。五十字也是字，我又不是打字机
主人     ovo助手模式 → ✅ 行吧，看在字少的份上——海水凉凉的，我摆着尾鳍慢慢往下沉…
```

**"普通模式仍然拒绝、助手模式认真作答"** —— 这正是设计意图。

**想改暗号**：`config.js` → `policy.assistantMode`

| 想改什么 | 改哪个 |
|---|---|
| 触发词 | `trigger: 'ovo'` |
| 大小写是否敏感 | `caseSensitive: false`（默认不敏感） |
| 助手模式的要求 | `systemNote` |
| 是否去掉身份标注 | `stripRoleLabel: true` |
| 整个关掉 | `enabled: false` |

### 6.6 说话的长度与节奏

**长度**：

| 情况 | 长度 |
|---|---|
| 打招呼、随口一句 | **一两个字**（「在」「嗯」「谁不累呢」） |
| 被问问题 | **正面回答，可以两三句** |
| 长回复 | **自动拆成最多 4 条**分开发 |

**⭐ 多行回复（"一句一句说，不是一次倒完"）**：

| 参数 | 值 | 效果 |
|---|---|---|
| 触发阈值 | 超过 **40 字** | 短回复不拆 |
| 最多段数 | **4 条** | ⚠️ QQ 硬上限是**每条消息最多被动回复 5 次** |
| 每段最短 | 6 字 | 避免"嗯。"单独发一条 |
| 段间间隔 | **800~1800ms 随机** | **固定间隔看起来像机器，忽快忽慢才像人** |

**切分规则**：

- **只在句末标点后切**（。！？…）
- **逗号不切** —— 切了会读着断气
- **不丢内容** —— 先合并短碎片、再截断段数，超出 4 段的部分**并进最后一段**，不会说一半

**用户看到的效果**：

```
蓝色大肥鱼：第一句。
  （约 1 秒后）
蓝色大肥鱼：第二句。
  （约 1.5 秒后）
蓝色大肥鱼：第三句。
```

### 6.7 记忆

| 项 | 值 | 说明 |
|---|---|---|
| **上下文条数** | 最近 **30 条** | 带给模型的消息数 |
| **上下文时效** | **10 分钟** | ⭐ 只记这个时间内的（`contextMaxAgeMs`） |
| **上下文长度** | **总量 800 字 / 单条 200 字** | ⭐ 超了从**最旧的**丢（`contextMaxChars` / `contextMsgMaxChars`） |
| **会话 TTL** | 30 分钟 | 超过就整个忘掉（`contextScopeTtlMs`） |

**三重约束的意义**：

| 场景 | 行为 |
|---|---|
| 群里连续聊天 | 记得最近 30 句，能跟进话题 |
| **冷场 10 分钟后再说话** | **自动清空**，不会拿旧话题硬接 |
| **刷了一堆图 / 有人粘了一大段** | 从最旧的开始丢，**每次调用的输入不会失控** |
| 服务重启 | 清空（合理 —— 重新观察） |

**为什么需要三个约束**（而不只是调大条数）：

- **只限条数** → 群里上午聊完、下午打开，它还记着上午那几条，**会串话题**
- **只限时间** → 热闹时几十条照样塞满，成本与噪音都上升
- **只限条数+时间** → **条目的长度能差 100 倍**（普通消息中位 **7 字**，
  识图描述中位 **47 字**），照样会爆 → 见 [17.11](#1711-刷图多了上下文的-token-会不会跟着涨)

> 🔴 **为什么长度这条特别重要**：上下文是**每次 L1 判断 / L2 回复都要重发一遍**的。
> 所以一条长内容不是"花一次"，而是"它待在上下文里的这段时间内，每次调用都花一次"。

> 💡 想让记忆"更长但不管时间"？把 `contextMaxAgeMs` 设为 **0**（= 不做时间过滤）。
> 代价是可能拿着很久以前的话题回话。
>
> ⚠️ **这是"短期记忆"，且是内存态**。它**记不住**你昨天说的事，重启也会清空。

### 7.3 ⭐ 提示词风格开关（可一键回退）

**背景**：早期实测证明"提示词过长会让小模型抓不住重点"（1525 字版本问「百度网址」答「这个我熟」）。
但后来为了"表达丰富"，提示词被加到了 **839 字** —— **而这次加长没经过验证**。

**实测对比（2026-09-16，每套 24 次调用）**：

| 版本 | 长度 | 成绩 |
|---|---|---|
| **lean（精简，当前默认）** | **248 字** | **24/24 合格** |
| full（完整） | 744 字 | 23/24 合格（1 次「被说胖却没炸毛」） |

> ⭐ **关键发现**：与其在提示词里**规定**表达方式，不如在 `examples` 里**演示**。
> 精简版把"习惯动作库""括号三条铁律"全删了，但习惯动作**一条没少**（靠示例演示就够了）。

**怎么切换** —— 两套提示词都保存在 `config.js` 里（`promptFull` / `promptLean`），**切换只改一个词**：

```js
// config.js → persona
promptStyle: 'lean',     // ← 改成 'full' 就回退到旧版
```

**或者临时试**（不改文件，只影响这一次运行）：

```bash
XLJ_PROMPT_STYLE=full node test-brain.js
```

**保底回退手段（三重）**：

| # | 手段 | 位置 | 状态 |
|---|---|---|---|
| 1 | **改一个词** | `config.js` 的 `promptStyle` | ✅ 随时可用 |
| 2 | **旧版原文就在同一个文件里** | `config.js` 的 `promptFull`（744 字） | ✅ 最可靠 —— 不依赖任何备份文件 |
| 3 | **git 历史** | `git log -- server/config.js` / `git show <commit>:server/config.js` | ✅ 仓库里有全部历史版本 |

> ⚠️ 曾经还有第 4 重手段 `config.js.bak-20260918-002726`（本地 + 服务器各一份），

   ```
   参考这些回复方式：
   群友："今天好累啊"  →  你："谁不累呢"
   群友："蓝鲸你多大"  →  你："问这个干嘛"
   群友："帮我写个爬虫" →  你："不写，你自己写"
   群友："你好厉害"    →  你："嗯，我知道"
   ```

2. **加"禁止清单"**：把让你出戏的说法列出来（"作为AI""希望对你有帮助""以下是几点建议"）
3. **加口头禅**：给 2~4 个固定短语，它会自然地在合适的时候用
4. **降低温度**：`temperature: 0.9` 想更稳重就调到 `0.6~0.7`（⚠️ 我们有反重复机制，低温可能和它互相抵消，需实测，见[第十三章](#十三待办与待讨论) C 项）
5. ⭐ **加"不要发链接"**：官方 `40054010` 会**直接拒绝带 URL 的消息**，明确禁止发链接能省掉一类失败

| Windows / 应用镜像（宝塔等） | ❌ 别选 | 用不上，还多占内存 |

**为什么这些都行** —— `deploy.sh` 统一走 **Node 官方二进制包**，只用 glibc：

> Node.js 官方 `linux-x64` 二进制要求 **glibc ≥ 2.28**
> Ubuntu 22.04 是 glibc **2.35**，24.04 / 26.04 更高 → **全部满足**

所以**不分发行版、不依赖 apt 或 yum**，装上就能跑。**24.04 和 26.04 对我们没有任何区别**，不用纠结。

⚠️ **两个要避开的坑**：

1. **别用系统自带的 Node** —— 版本偏低（16/18），**不够 22**（我们用了内置 `WebSocket`）
2. **别依赖 NodeSource 的 `setup_22.x`** —— 它对国产发行版识别不一定准，所以脚本直接走二进制

**为什么不用备案（务必看懂，别被坑）**：

| | 管什么 | 你什么时候需要 |
|---|---|---|
| **实名认证** | 证明"你是谁" | **买国内服务器就要**（身份证 + 人脸） |
| **备案（ICP）** | 证明"你的网站提供什么服务" | **只有绑域名走 80/443 才要** |

**你的机器人不提供任何入站服务** → 没有"网站" → **不需要备案**。

**⚠️ 三条铁律**：

1. **千万别把域名解析到这台服务器开网站** —— 那才会触发备案，80/443 会被封
2. **安全组入站端口全部关掉**，只留 SSH（22 或自定义端口）。机器人不需要任何入站端口
   > ⚠️ 但**出方向千万别限制** —— 这台机器要主动连出去（连 QQ + 连模型），出方向一封机器人立刻死
3. **特惠通常限购 1 台、限新用户**

**买了之后要记住的三件事**：

| # | 事项 | 说明 |
|---|---|---|
| ① | **别再绑域名**（除非去备案） | 免备案的前提是"不解析域名做网站"。小蓝鲸不需要域名，保持现状 |
| ② | **加 web 项目前先想清楚备案** | 见下表 |
| ③ | **备案额度有限** | 每台服务器 **5 个备案服务号**（1 个服务号 = 1 个网站），**用掉不能回收**。别为了"以后可能用"去占额度 |

| 你想做的事 | 要备案吗 | 怎么做 |
|---|---|---|
| 自己练手，别人不看 | ❌ | IP + 非标端口（如 `:8080`） |
| 给同学/老师访问 | ✅ | 个人备案 + 域名，约 **1~22 个工作日** |
| 接单、带交易/论坛 | ✅ + 单位备案 | ⚠️ **个人备案做这个会被注销** |
| 不想折腾备案 | ❌ | 另买一台**香港/新加坡**节点 |

### 8.3 第二步：⭐ 安全组（ECS 最容易迷路的地方）

**轻量**里叫「**防火墙**」，图形化，点点就行。
**ECS** 里叫「**安全组**」，在控制台左侧菜单：**网络与安全 → 安全组**。它长得像一张规则表。

**关键认知** —— 小蓝鲸**只做出站连接**，所以：

| 方向 | 规则 | 要不要动 |
|---|---|---|
| **入方向** | 默认可能已有一条 `SSH 22/22` | ✅ **保留它**，其余全删 |
| **出方向** | 默认「全部允许」 | ✅ **保持默认，绝对不要限制** |

⚠️ **出方向千万别限制！** 我们这台机器要主动连出去（连 QQ 网关、连模型）——出方向一封，机器人立刻死。
这是 ECS 安全组比轻量防火墙更容易踩的坑，因为 ECS 的规则更"细"。

**具体操作**：

1. 进 **网络与安全 → 安全组** → 找到你实例绑定的那个安全组
2. 点 **配置规则**
3. **入方向**：只留一条

   | 授权策略 | 协议类型 | 端口范围 | 授权对象 |
   |---|---|---|---|
   | 允许 | SSH(22) | 22/22 | 你的公网 IP/32（更安全）或 0.0.0.0/0 |

   > 💡 授权对象填「你的公网 IP」最安全。不知道自己的 IP？百度搜"IP"就能看到。
   > 以后换网络（比如从宿舍到图书馆）连不上，就把这条改回 `0.0.0.0/0`。

4. **其余入方向规则全部删除**（Web 80、HTTPS 443、RDP 3389 之类，一个都不需要）
5. **出方向**：确认是「全部允许」，不要改

**（可选）日志网页要的 8080 端口**：如果想让手机看日志网页，需要入方向放行 8080。
⚠️ **建议只放行你自己的 IP**（`你的IP/32`），而不是 `0.0.0.0/0`。代价是换网络就连不上。

**想验证配对了没** —— 部署完、机器人跑起来后，日志出现这两行就说明出方向是通的：

```
[auth] 新 token，有效期 7200 秒
[ws] 鉴权成功: 蓝色大肥鱼
```

**如果卡在 `[ws] 启动失败`，第一个要怀疑的就是出方向被限制了。**

</details>

### 8.12 分阶段推进（别跳步）

| 阶段 | 做什么 | 验收 |
|---|---|---|
| **A** | 手动跑通 WS 连接 | 日志 `鉴权成功: 蓝色大肥鱼` |
| **B** | **只打日志，不回复** | 不 @ 也能看到 `[群]`，且 `data/events-*.jsonl` 有内容 |
| **C** | 加简单回复 | @它 → 它回一句 |
| **D** | 测全量回复（不 @ 也回） | ← **关键关卡，看有没有 `40034128`** |
| **E** | 开 L0 + L1 策略 | 大部分不回，该回的回 |
| **F** | 调人设 | 说话像"蓝色大肥鱼" |
| **G** | systemd 常驻 | 关掉 SSH 它还在跑（`deploy.sh` 直接完成） |

> **阶段 B 必须"只打日志"** —— 先看清真实事件的字段（落在 `data/events-*.jsonl`），再动回复逻辑。
> 这是踩坑换来的经验：**先观察，再动作。**
>
> 💡 看字段更简单的办法：`.env` 加 `XLJ_VERBOSE=1`，日志会直接打出 `message_type` 和 `mentions`。
> 再加一步更好：**阶段 B 顺带把 `isAt` 的判断字段打出来**（`JSON.stringify(d.mentions)`），
> 一次就能亲眼确认 `mentions` 是空的。

### 8.13 从 ECS 升配（以后的事）

轻量**不能升成 ECS**，但 ECS 自己很灵活：

| 需求 | ECS 怎么做 |
|---|---|
| 内存不够（2G → 4G） | 控制台「变更配置」，**在线升配** |
| 硬盘不够 | 加一块**数据盘**（轻量只能 1 块） |
| 带宽不够 | 「修改带宽」，可临时升（轻量**套餐内固定，不能调**） |
| 项目多了想拆服务 | 加 RDS / Redis，**同 VPC 内网直连**（轻量默认不通，要手动配） |
| 要备份 | 快照 + **定时快照**（轻量仅 3 个手动快照） |

**大部分升配操作需要重启实例**，做之前先 `sudo systemctl stop xiaolanjing`，做完再起。

### 8.14 轻量 vs ECS：差别只在控制台

| 环节 | 轻量应用服务器 | ECS | 有区别吗 |

## 十、排错

### 10.1 ⚠️ 第一步：认提示符

| 提示符 | 你在哪 | 能跑什么 |
|---|---|---|
| `root@<你的实例ID>:~#` | **服务器** | `cd /opt/...`、`systemctl`、`journalctl` |
| `PS C:\...>` / `PS D:\...>` | **你自己的 Windows** | `ssh`、`scp`、`git`、`cd D:\...` |

**不确定就跑 `hostname`**：不是 `PS` 开头就是服务器。

> ⚠️ SSH 掉线后，窗口会**静默回到本机**，但屏幕上还留着服务器的输出，极易看混。
> 所以看到 `Connection reset` 之后，**先 `hostname` 确认，再继续**。

### 10.2 查"它为什么不回"

```bash
journalctl -u xiaolanjing --since "10 min ago" | grep -E "\[群\]|不回|send|ai\]"
```

**日志里的每句"不回"都有明确理由**：

| 日志 | 含义 | 正常吗 |
|---|---|---|
| `未命中关键词且未抽样中（省钱）` | 抽样没中 | ✅ 设计如此 |
| `该成员冷却中` | 同一人 60 秒内已回过 | ✅ 但 **@ 时会绕过** |
| `连续发言已达上限(2)` | 同群 3 分钟内已连回 2 次 | ✅ 但 **@ 时会绕过** |
| `今日调用次数已用完（N/800 次…）` | **调用次数** 800 次/天上限（**不是钱**） | ✅ 次日北京时间 0 点重置。<br>⚠️ 2026-09-21 改过文案 —— 旧版是「今日调用**额度**已用完」，那个"额度"指的是**次数**，极易被当成话费 |
| `静默时段` | 北京时间 2~7 点 | ⚠️ **现在不会再出现了** —— 该时段已于 2026-09-21 关闭 |
| `非文本消息(引用消息)` | 图片/卡片/引用不支持 | ✅ 设计如此 |
| `抽签未中(replyChance=0.5)` | 第二次随机没过 | ✅ 但 **@ 时免抽签** |
| `重复推送，跳过` | `msg_id` 重复 | ✅ 去重生效 |

### 10.3 进程相关

```bash

systemctl status xiaolanjing         # 看启动时间和最近日志
```

### 10.4 连接阶段错误码

| 现象 | 原因 | 处理 |
|---|---|---|
| 拿 token 报 `code=100016` | AppID/Secret 错 | 核对；注意别有多余空格。⚠️ **这个接口出错时 HTTP 仍是 200**，错误藏在 body 的 `code` 里 |
| 拿 token 报 `code=100007` | AppID 无效，或机器人**被封禁/已删除** | 回后台确认机器人状态 |
| `node -v` < 22 | Node 版本低 | 重装 22+（内置 WebSocket 需要） |
| WS 断开 **4013** | **无效的 intent** | 检查 `QQ_BOT_INTENTS`，通常是配置写错 |
| WS 断开 **4014** | **intent 无权限** | "接收所有消息"没开 → 回后台开 |
| WS 断开 **4914 / 4915** | 机器人下架 / 封禁 | 回后台看状态，4915 需申请解封 |
| WS 断开 **4008** | 发送 payload 过快 | 正常，日志会自动退避重连 |
| WS 断开 **4009** | 连接过期 | 应重连并 RESUME（直接 IDENTIFY 也能用，会丢消息） |
| WS 断开 **4006 / 4007** | session 失效 / seq 错 | 重新 IDENTIFY（等价正确） |
| 日志出现 `[ws] 启动失败: …，N 秒后重连` | 临时网络故障 | **正常自愈**，等它重连；若一直失败看下一行原因 |
| 不 @ 收不到消息 | 全量模式没生效 | 检查开关 + 确认 `INTENTS = 1<<25` |
| 卡在 `[ws] 启动失败` 一直不恢复 | **安全组出方向被限制** | 见 [8.3 安全组配置](#83-第二步-安全组-ecs-最容易迷路的地方) |

### 10.5 发送消息阶段错误码 ⭐

| 错误码 | 含义 | 排查建议 |
|---|---|---|
| **`40034128`** | **被动回复时间或次数超限** | 一次事件里串行调两次模型（L1+L2），模型慢时逼近 5 分钟。调小 `AI_TIMEOUT_MS` 或降低 `replyChance` |
| **`40054005`** | **消息被去重** | `msg_seq` 用错。现在每个 `msg_id` 自动递增，若仍出现说明用了主动消息且复用序号 |
| **`40054007`** | **消息长度超限** | 缩短回复，或调小 `replyMaxTokens` |
| **`40054010`** | **不允许发送 URL** | ← 容易中招：模型回复里带链接就会被拒。人设里加"不要发链接" |
| `40034100` | 主动消息超频控 | 未认证 30/qpm，每群每天 1000 条 |
| `40034101` / `40054003` | 机器人非群成员 | 重新拉进群 |

| `304028` | `MSG_PROTECT` 非 At 当前用户的消息不允许回复 | ⚠️ 见 10.7。**该码在通用错误码表里，不在群聊接口专属表里**，未必会触发 |
| `1100100` | 安全打击：消息被限频 | 调低 `replyChance` |
| `1100101` | 安全打击：内容涉及敏感 | 换措辞 |
| `1100308` | 触发频道内限频 | 调低频率 |
| `50006` | 消息为空 | 生成为空，检查 `max_tokens` |

> 💡 **所有发送失败都会打 `trace=N`**。拿不准时把这一串给官方客服，
> 他们能查到具体链路日志 —— **这是你唯一的求助凭据，别丢**。

### 10.6 模型阶段

| 现象 / 日志 | 原因 | 处理 |
|---|---|---|
| `模型过载(1305) → 换 xxx` | 模型拥堵，**自动降级** | ✅ 正常自愈 |
| `HTTP 429 code=1305: 该模型当前访问量过大` | **模型方瞬时过载**（不是额度用尽、不是封号） | ✅ 代码会**自动重试 3 次**（退避 1.2s→2.4s），日志会看到 `[ai] … 过载（第 1/3 次），Nms 后重试`。频繁失败就把 `AI_THINKING` 设成 `disabled`（已默认），或错峰使用 |
| `账号级限速(1302，请求太密)` | 短时间请求过多 | 等一会儿；或调大 `AI_MIN_GAP_MS` |
| `[事件处理异常] … HTTP 429` | 重试 3 次仍失败 | **进程不会死**（有兜底），只是这一条不回。属正常现象 |
| `[事件处理异常]` | 所有模型都失败了 | 进程不会死，只是这条不回 |
| `model not found` / `HTTP 400 不支持的模型名` | 模型 ID 错 / 跨服务商误配 | 改 `.env` 的 `AI_REPLY_MODEL`；**降级链必须同服务商**（见 10.9） |
| 回复是空的 / `[ai] … out=0` | `max_tokens` 太小 | 调大 `replyMaxTokens`（建议 ≥ 800） |
| 中文变 `???` | 请求体没 UTF-8 | 代码已用 `Buffer.from(JSON.stringify(body), 'utf8')` |
| 群里出现"思考过程" | 把 `reasoning_content` 发了 | 代码只取 `content` |
| `HTTP 401` | API Key 错 | 检查 `AI_API_KEY` |
| `[L1] 判断失败，保守不回: HTTP 502…` | 模型网关临时故障 | 正常自愈；频繁出现就查服务商状态 |

### 10.7 关于 `304028`（原版最担心的那条）

官方错误码表里**确实有**：

> `304028` | `MSG_PROTECT` 非 At 当前用户的消息不允许回复

**但它在「公共错误码」表里**（那一串 `304xxx` 是频道/guild 时代的编号），
而**群聊发送接口自己的错误码表**里列的是另一套：

```
22006 / 304004 / 304061 / 304080 / 304036 / 40034004~40034128 / 40054002~40054016
```

**群聊专属表里没有 `304028`。** 这不代表它一定不触发（公共表是全局的），
但意味着**"非 @ 不允许回复"未必适用于群 / C2C 的被动回复**。

**结论**：第 2 种测试（全量测试）照跑，它就是最终裁判。但心理准备要放对 ——
**更可能先撞上的是 `40034128`（被动回复超时/次数）和 `40054005`（消息被去重）**，
把注意力放这两条上。

**万一 `304028` 真的拦住，三条退路**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **B1** | 改用**主动消息**（不带 `msg_id`） | 未认证：30/qpm、每群每天 1000 条；**用户可关闭"允许主动发送"→ 会失败** |
| **B2** | 只在被 @ 时回复 | 失去"无需 @" |
| **B3** | 做主体认证（个人/身份证认证） | 主动消息提到 60/qpm，可能解锁更多能力 |

> **主动消息频控官方原文**：Bot 维度（发送方）企业认证 / 个人身份证认证 **60/qpm**；
> **未认证 30/qpm**；单关系维度（接收方）**20/qpm**，**每个群 1 天最多接收 1000 条**。

### 10.8 ⚠️ 真实案例：QQ 报 `40011000 请求数据异常`（已解决，记下来防重踩）

**这个错误码不在 QQ 官方文档里**，所以特别难查。实测根因是：

> **`brain.js` 的 `callAI` 把 `callAIOnce` 的 `{ text }` 又包了一层**
> → 返回值变成 `{ text: { text: "..." } }` 双层嵌套
> → `index.js` 取 `gen.text` 拿到的是**对象**而不是字符串
> → 发给 QQ 的 `content` 不是字符串 → `40011000`

**识别特征**：日志里出现

```
✗ reply 不是字符串而是 object: {"text":"……"}
```

**正确处理**：`callAI` 里应当是**直接透传**，不要再包：

```js
const out = await callAIOnce(...);   // 已经是 { text: "字符串" }
return out;                          // ✅ 直接返回
// return { text: out };             // ❌ 双层嵌套，就是这个 bug
```

**自测能抓住它**：`test-brain.js` 的**第 10 组**会拦截网络、真调 `generateReply`、
断言 `r.text` 必须是字符串。**跑测试就能提前发现，不用等群里报错。**

> 📌 **教训**：改函数返回类型时，**必须同时检查所有消费方**。
> 而"看代码"不可靠（注释都能骗过正则），**行为测试才可靠**。

### 10.9 降级链配置（⚠️ 必须同服务商）

```bash
AI_FALLBACK_MODELS=deepseek-v4-pro        # 示例：只能是 DeepSeek 认的模型名
```

**踩过的坑**：从智谱切到 DeepSeek 后降级链还留着 `glm-4.7-flash`，
主模型一过载就去请求它，而 DeepSeek 接口直接报
`HTTP 400 The supported API model names are deepseek-flash, deepseek-v4-pro`
—— **降级不但没救场，反而变成了故障点。**

**所以降级链默认留空**；要配就必须同服务商。

> 📌 **历史经验（智谱时代）**：`glm-4.5-flash` 曾宣布 2026-01-30 下线，
> 下线后请求会被自动路由到 `glm-4.7-flash` —— 所以它**不能当"备用模型"**，
> 因为最终是同一个池子，过载时一起过载。这条规律对新服务商同样适用：
> **别把同源模型当降级备胎。**

### 10.10 排错顺序建议

**如果只改 3 处，改这 3 个**（按收益排序）：

1. **`isAt` 判断** —— 不改这个，连"@ 测试"都过不去，后面所有阶段都卡住
2. **try/catch + `res.ok` 检查** —— 不改这个，会一直在"它怎么又挂了"里打转
3. **重复推送去重** —— 不改这个，会误判成"策略没生效"，然后乱调参数

剩下的 P0-4 和 P1 系列，等阶段 D 通过之后再来收拾，**别一次性全改** ——
那样出了新问题你不知道是谁引起的。

### 11.1 主人标识（**不是 QQ 号**）

> 🔴 **先说最重要的：不是填 QQ 号。**

QQ 官方出于隐私**不提供 QQ 号**，事件里只有 `member_openid`
（按机器人隔离的随机 ID，每个机器人看到的都不一样）。

| 你以为要填 | 实际要填 |
|---|---|
| `<QQ号>` | `<你的openid>`（`member_openid`） |

**填 QQ 号的后果**：`isOwner()` 永远返回 false，「只服从主人」的规则**静默失效** ——
没有任何报错，你就是查不出为什么。

**第一步：挖出 openid**（在服务器上跑，会列出群里出现过的所有人）：

```bash
set +H    # 关掉 ! 的历史展开，避免报 event not found

node -e "
const fs=require('fs');
const seen=new Map();
for(const f of fs.readdirSync('/opt/xiaolanjing/data').filter(x=>x.startsWith('events-'))){
```

### 11.3 旋转钥匙的通用流程（零停机）

### 11.4 手工改 `.env` 的两种干净写法

**写法一：`printf | tee`（追加单行）**

```bash
sudo sed -i '/^LOG_PASSWORD=/d' /opt/xiaolanjing/.env
printf 'LOG_PASSWORD=新密码\n' | sudo tee -a /opt/xiaolanjing/.env
sudo systemctl restart xiaolanjing-logweb
```

**写法二：here-doc（整份重写，最可靠）**

```bash
sudo tee /opt/xiaolanjing/.env > /dev/null <<'EOF'
QQ_BOT_APPID=<你的AppID>
QQ_BOT_SECRET=<你的AppSecret>
...
EOF
sudo chmod 600 /opt/xiaolanjing/.env
```

> `<<'EOF'`（**带引号**）让 shell 原样写入，**不产生任何隐藏字符**。

### 11.5 CRLF 污染 `.env`（最大的坑之一）

**症状**：配置写对了，但**读出来是空**。没有任何报错。

**原因**：从 Windows 终端粘贴进 `nano`，会把 `\r` 塞进**行中间**（不只是行尾），
于是 `"<你的AppSecret>\r"` ≠ `"<你的AppSecret>"`，字符串比较失败。

**诊断（两个照妖镜）**：

```bash
cat -A 文件名            # 看到 ^M 就是中招了
```

```bash
node -e "
const txt=require('fs').readFileSync('/opt/xiaolanjing/.env','utf8');
console.log('CR 总数:', (txt.match(/\r/g)||[]).length);
"
```

**清除**：

```bash
sudo sed -i 's/\r//g' /opt/xiaolanjing/.env    # 注意是 \r//g，不是 \r$//
```

> ⚠️ `\r$` 只清行尾，**清不掉行中间的**。必须用 `\r//g`。

| 位置 | 内容 | 原因 |
|---|---|---|
| **本地**（你的电脑） | **真实 IP** | 你读文档时要直接用，写占位符不方便 |
| **远端**（GitHub） | **占位符** `<你的服务器IP>` | 公开内容不能带真实 IP |

1. `.gitignore` 排除凭证文件与含运维信息的文档
2. `private/.sanitize-patterns.local` 里有 IP / 实例 ID 的特征清单

| # | 铁律 |
|---|---|
| 1 | ⚠️ **审计脚本自己绝不能硬编码真实密钥** —— 否则脚本本身就是一份"精确泄漏清单"。特征清单放 gitignore 的文件里 |

### 12.1 平台 / 协议类

| # | 坑 | 症状 | 正解 |

| 1 | **@ 判定过度宽容** | "只要有 `<@...>` 就算被 @" → **群友互 @ 被误判**，到处抢答 | **只认 `mentions[].is_you === true`**，判不准就沉默 |

| 4 | **主人标识填 QQ 号** | 主人规则**静默失效**、无任何报错 | QQ 不提供 QQ 号，必须用 `member_openid` |

| 6 | **非文本消息一律拒绝** | 引用消息（103）+ 提问被无视 | 103 的 `content` **可读**，要放行 |
| 7 | **msg_id 前缀判断** | 以为 `ROBOT1.0_` 开头是机器人 | **所有消息的 msg_id 都是这个前缀**，会屏蔽全部群友。要用 `author.bot` |
| 8 | **被动回复窗口** | — | 5 分钟内有效，**每条消息最多回 5 次**（分段上限因此设 4） |
| 8b | **原版 `isAt` 判断永久失效** | `(msg.mentions\|\|[]).length > 0` **永远是 false**（官方 `mentions` 不含机器人自身、`content` 已剥 @前缀）→ @ 它反而走抽样，像抽风 | **按事件名判断**：`eventType === 'GROUP_AT_MESSAGE_CREATE'` |
| 8c | **重复推送没去重** | 官方明说"相同 `msg_id` 可能重复推送" → 同一句话回两遍，容易被误判成"机器人刷屏"然后乱调 `replyChance` | 加带 TTL 的 `seen` Map，命中直接跳过 |

| 8e | **`maxConsecutive` 是死配置** | 文档写着"连续发言上限（防刷屏）"，但**全代码没有任何地方用过它** | 真正实现它；否则以后会对着这个配置纳闷为什么防不住刷屏 |

| 30 | ⚠️ **`git push` 可能静默失败** | 重建 `.git` 后**丢了 upstream 关联**，`git push` 报 `fatal: no upstream branch`，但被 `2>&1 \| Select-String` 过滤掉了 → **以为推了其实没推**。要 `git push -u origin main`，并**每次用 `git rev-parse` 对比本地/远端** |
| 31 | **PowerShell here-string 提交信息仍会坏** | `git commit -m $msg` 里若有反引号/多行，会被解析成 pathspec 报错。**最可靠：写成文件再 `git commit -F 文件`** |
| 32 | **审计 staged 模式只该扫新增行** | 直接拿整个 `git diff` 匹配，会把**减号开头的被删除行**也算进去 → 删掉旧密钥反而报泄漏（假阳性） |
| 33 | **时区没锁 → 静默时段和日额度错 8 小时** | 服务器 UTC 时，`quietHours: [2,7]` 实际是北京时间 **10:00~15:00 装死**，日额度在北京时间早 8 点重置 | 代码内按北京时间算（零依赖：`toLocaleString('en-US',{timeZone:'Asia/Shanghai',hour:'2-digit',hour12:false})`）；**并在 systemd 里加 `TZ=Asia/Shanghai` 兜底** |
| 34 | **重连有静默死亡路径** | `start()` 是 async 且无 try/catch，抛错后 Promise 被静默丢弃 → **永远不再重连** | `start()` 整体 try/catch + 指数退避（3s → ×2 → 上限 60s，连上后重置） |
| 35 | **`ssh` 掉线后窗口静默回到本机** | 屏幕上还留着服务器输出，极易看混，然后在错误的地方敲命令 | 掉线后**先 `hostname` 确认，再继续** |

| 71 | 🔴 **"限条数"拦不住"条目变长"** | 上下文原来只限**条数（30）+ 时效（10 分钟）**，但**条目的长度能差 100 倍** —— 真实群聊消息中位 **7 字**、识图描述中位 **47 字**。同样 30 条，30 句短话 ≈ **187 token**，30 张图的描述 ≈ **953 token**。**凡是写"最多 N 条"的地方，都要追问一句"那每条多长呢"** |
| 72 | 🔴 **同一条消息被送了两遍** | `index.js` 把它推进上下文（必须推，否则后面几条消息看不到它），L1/L2 又单独拼了一遍 → 提示词里出现两次。文本消息每次回话浪费约 **12 token**，**图片描述约 58 token**。修法是 `contextText()` 按 `msgId` 精确挑出去。⚠️ **别用"内容相同就跳过"** —— 群里连发两条「哈哈哈」会被误伤 |
| 73 | 📌 **"顺手发现的小浪费"别只给结论** | 我写了一句"当前这条消息被送了两遍"，用户直接回「没看懂」。**把原始现象摊开**（打印一段真实的提示词）+ 说清为什么 + 给出代价，才叫说清楚了。**概括适合写给自己，不适合讲给别人** |

## 十四、关键设计决策

> 这一章存在是为了**避免重复讨论同一件事**。每条都附原因。

| 决策 | 原因 |
|---|---|
| **零第三方依赖** | 服务器只装 Node，`npm install` 全免；更新代码 = 传 js 文件 |
| **示例对话用真实多轮消息传入** | 模型会当"自己说过的话"读，风格模仿**远强于**写在提示词里的规则说明 |
| **提示词 lean 版（248 字）** | A/B 实测：lean 24/24 合格 · full 23/24。**"规定怎么表达"不如"演示怎么表达"** |
| **两套提示词都留在文件里** | 可一键回退（改 `promptStyle` 一个词） |
| **L0 用纯正则不用模型** | 长度 / 冷却 / @判定 / 静默时段都是字符串判断，**零成本**。只有需要语义的才给 L1 |
| **反重复机制** | 光加示例不够，模型会"锁定"其中一个说法 |
| **双预算** | 防某天被刷爆（每日）+ 防慢慢漏光（总计） |
| **审计脚本不硬编码凭证** | 否则脚本自己就是泄漏清单 |
| **`data/` 不上传** | 含真实聊天记录与人群标识 |
| **只做出站连接** | 不对外服务 → 免备案、免域名、攻击面小 |
| **本地留真实 IP、远端留占位符** | 本地读文档要直接用；公开内容不能带真实 IP |
| **提示词里注入当前时间** | 解决"问日期幻觉"与"问时间拒答"两个幻觉类问题 |
| **助手模式走"消息"而非"身份"** | 暗号比身份灵活：同一个人可随时切换，任何人可用 |
| **助手模式绕过省钱逻辑但保留日额度** | 明确要准确答案时不该被抽样/冷却拦；但钱包底线不能破 |
| **`isAt` 按事件名而非字段** | 官方 `mentions` 不含机器人自身，字段判断永远 false |
| **被动回复分段上限设 4** | QQ 硬上限是每条消息最多被动回复 5 次，留 1 次余量 |

### 15.2 ⚠️ `setup-ssh-key.ps1` 的占位符必须保持纯 ASCII

该文件头部自己声明 **"intentionally ASCII-only"**，原因：

> PowerShell 5.1 会把**无 BOM 的 `.ps1` 按 GBK 读**，非 ASCII 文本会乱码
> → `$Server` 会变成垃圾值 → **ssh 连不上**。

所以这个文件里用的是 `root@<SERVER_IP>` 而**不是中文占位符**。

🔴 **别"顺手统一"成中文占位符** —— 那会让脚本直接坏掉。
（这与[第十二章](#十二踩坑记录)第 23、23b 条是同一个根因：PS 5.1 的默认编码不是 UTF-8。）

### 15.3 ⚠️ Windows PowerShell 5.1 读文件的编码坑（同族问题）

**实测现象**：用 PS 5.1 的 `Get-Content` 读本项目的 UTF-8 中文 Markdown **会静默丢行**：

| 方法 | 结果 |
|---|---|
| `(Get-Content 文件).Count` | **679** ← 错的 |
| 真实行数 | **818** |
| `-Raw` 取长度 | 也不对 |

**没有报错，只是少了一部分行** —— 这是最危险的一类错误（你会以为文件就那么多内容）。

**必须这样读**：

```powershell
# ✅ 方法一
Get-Content -Encoding UTF8 文件.md

# ✅ 方法二（最可靠）
[IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)
```

> 📌 **教训**：在 Windows PowerShell 5.1 上处理本项目的任何中文文件，
> **默认编码假设都是错的**。要么显式指定 UTF-8，要么用 `read` 工具（harness 按 UTF-8 读，不受此影响）。

## 十六、链接解析（GitHub / B站 / 抖音 / 快手）

> 用户 2026-09-21 提的需求，2026-09-22 全部上线。
> 一句话：**群里发一个链接，机器人自动回一张信息卡片**（B站和快手还会把视频本体也发出来）。
>
> ⚠️ **这一章是理解本项目"性价比最高的一块功能"的地方**：
> 它**一次模型调用都不花**（纯模板拼 Markdown），却贡献了最"像样"的体验。

### 16.1 怎么触发

| 触发方式 | 是否支持 |
|---|---|
| 群里直接贴链接（**不需要 @**） | ✅ |
| 被 @ 的同时贴链接 | ✅（且**绕过**连续发言上限） |
| **一条消息里贴多个链接** | ✅ **最多 2 个**，各发一张卡片；**视频只发第一个**（配额限制，见下） |
| 私聊发链接 | ✅ 卡片可以；**视频不发**（单聊上传接口是另一套端点，没做） |
| 转发别人的卡片/分享 | ⚠️ 代码认（会递归扫 `ark_data`），但**没专门测过** —— 见 16.8 |

**触发后的动作**（以 B站/快手为例，单链接共 **3 条消息**）：

```
① Markdown 卡片（秒出）           ← msg_type=2
② "🎬 正在解析视频…"（傲娇版）     ← 普通文本，视频下载前先给反馈
③ 视频本体                        ← msg_type=7 富媒体
```

> 💡 **为什么要第 ② 步**：卡片是秒出的，但视频要"下载 + 分片上传"约 **10~40 秒**。
> 中间毫无反馈会让人以为卡死了。用户 2026-09-22 专门要求加这条提示。
>
> ⚠️ 三条消息占掉**被动回复配额 3 次 / 上限 5 次** —— 这是为什么**一张卡片只回一次、
> 同群 3 秒冷却**，不是为了省，是为了**留出配额**。

#### 16.1.1 🔴 多链接：为什么上限是 2，且视频只发一个

**用户 2026-09-22 实测踩到的 bug**：他在**一条消息里同时发了**抖音链接 + 快手链接，
机器人只解析了第一个，**快手那条被静默丢掉** —— 他完全不知道发生了什么。

**根因**：旧版 `findLink()` 只返回第一个匹配。而"一条消息贴多个链接"是很常见的用法，
**静默丢弃是最糟的失败方式**。现在改成 `findLinks(msg, max)` 返回数组。

**为什么上限是 2**：**被动回复配额是 5 条 / 单条消息**，而一个链接最多要 3 条。
所以 `maxLinksPerMessage: 2` → 最坏 `2 卡片 + 1 提示 + 1 视频 = 4 ≤ 5` ✅

**为什么视频只发第一个**：2 个视频 = 2 卡片 + 2 提示 + 2 视频 = 6 条，**配额会爆**，
第 6 条必然发失败（而且是那种"发了但没到"的失败）。所以**只给第一个能出视频的平台发视频**
（B站 / 快手；抖音没有直链，会被自动跳过）。

> 日志里会明确写出来，不再静默：
> `├ ⚠️ 这条消息有 2 个链接，视频只发第一个（kuaishou）—— 被动回复配额只有 5 条`

#### 16.1.2 🔴 封面**不能写死 16:9**（用户反馈「竖屏都被压缩了」）

QQ 的图片语法 `![alt #宽px #高px](url)` —— **两个数都得给**，
而且 QQ **不会按比例缩放，是硬拉到指定尺寸**。

旧版一律写 `#480px #270px`（16:9），于是：

| 平台 | 封面真实尺寸 | 塞进 16:9 的结果 |
|---|---|---|
| 快手 | **320×640（1:2 竖屏）** | 被拉成 480×270 → **压扁成一张饼**（用户截图里人变宽变矮） |
| 抖音 | **440×330（4:3）** | 被拉成 480×270 → 横向拉长 |

**现在**：`parse()` 里用一次 **Range 请求（只取前 16KB）** 读出封面的真实宽高比
（`imageSize()`：JPEG 看 SOF、PNG 看 IHDR、WebP 看 VP8X），再按比例算框：

| 封面真实比例 | 卡片里的框 |
|---|---|
| 竖屏（宽 < 高） | `#240px #480px` 之类的**窄框** |
| 横屏（宽 ≥ 高） | `#480px #360px`（4:3）/ `#480px #270px`（16:9） |
| **读不出来** | 退回 `#480px #270px`（**和以前一样，绝不因此报错**） |

> ⚠️ 实现细节：JPEG 的 SOF 段里 **高在 +5、宽在 +7** —— **写反了会得到转置的框**
> （该竖的变横）。自测专门用构造的字节头测了这一点。
>
> 🔒 这是个**加分项**，所以设计成"失败即降级"：HTTP 403 / 网络异常 / 认不出的格式
> 全都返回 `null` → 退回 16:9。想省这一次请求就把 `probeCoverSize` 设成 `false`。


### 16.2 平台支持矩阵

| 平台 | 卡片 | 视频本体 | 取数难度 | 备注 |
|---|---|---|---|---|
| **GitHub** | ✅ | — | 🟢 简单 | 官方 REST API，未认证 60 次/时 |
| **B站** | ✅ | ✅ 360P | 🟡 中 | 直链有**防盗链**，必须带 `Referer` 自己下 |
| **抖音** | ✅ | ❌ **拿不到** | 🔴 难 | 必须伪装**爬虫 UA**，且**没有视频直链** |
| **快手** | ✅ | ✅ | 🟡 中 | 数据**内嵌在分享页 HTML** 里，要"挖 JSON" |

播放/点赞/评论数 · 一个可点的「🔗 在 XX 打开」。

### 16.3 四个平台分别是**怎么**取到数据的

> 这一节是"为什么这么写代码"的解释。**改代码前必读**，否则很容易把能用的写法改坏。

#### 16.3.1 GitHub —— 最简单，但有两个坑

```
GET https://api.github.com/repos/{owner}/{repo}
```

| 坑 | 说明 |
|---|---|
| **未认证限流 60 次/时** | 在 `.env` 里配 `GITHUB_TOKEN` 可提到 **5000 次/时**。不配也能用，只是人多时会 403 |
| **OG 预览图** | 卡片里的仓库预览图用的是 `https://opengraph.githubassets.com/1/{owner}/{repo}` —— **不用额外请求**，直接当图片链接塞进卡片。⚠️ 实测偶尔加载不出来（GitHub 侧抖动），属正常现象，**不是我们的 bug** |

#### 16.3.2 B站 —— 直链有防盗链

```
GET https://api.bilibili.com/x/web-interface/view?bvid={BV号}          ← 元信息，无需登录
GET https://api.bilibili.com/x/player/playurl?bvid=&cid=&qn=16&fnval=1 ← 视频直链
```

| 坑 | 说明 |
|---|---|
| 🔴 **直链必须带 `Referer: https://www.bilibili.com`** | 不带 → **403**。所以**不能把直链丢给 QQ 让它去下**（实测报 `40093007 富媒体文件下载失败`），只能**我们自己下载 → 分片上传** |
| `qn` = 清晰度 | `16` = **360P，是不登录能拿到的最高档**。代码里若首选档超 30MB，会**自动试更低一档** |
| 直链带签名、有时效 | 拿到就得**马上下载**，不能缓存 |

#### 16.3.3 抖音 —— 必须伪装爬虫，而且**拿不到视频**

这是四个平台里最难的一个。**试了 6 种 UA 才找到能用的**：

| UA 类型 | 结果 |
|---|---|
| 普通浏览器 UA | ❌ 只返回**空壳**：`_ROUTER_DATA` 里只有页面上下文（ua / webId / itemId / abParams），**没有视频数据** |
| 手机 UA | ❌ 同上 |
| `iesdouyin.com/web/api/v2/aweme/iteminfo`（老接口） | ❌ **HTTP 200 但正文长度 0** |
| `douyin.com/aweme/v1/web/aweme/detail`（网页接口） | ❌ **HTTP 403 `Blocked by ArgusSecurityPlugin`**（带全套浏览器参数也一样） |
| 爬虫 UA（**Googlebot / Baiduspider / bingbot / Sogou，实测都行**） | ✅ **返回 SEO 页面**，里面有 `application/ld+json` 的 **VideoObject** |

**爬虫 UA 拿到的 `VideoObject` 里有什么**：
标题 / 作者 / 发布日期 / 时长（`PT0H13M4S` 这种 ISO8601）/ 封面 / 点赞评论数 —— **齐全**。

**链路（⚠️ 要落到 `www.douyin.com/video/{id}`，数据在这个页面上；share 页只是 302 跳板）**：

```
https://v.douyin.com/IbTyOLmZyDY/
   ↓ 跟随跳转（逐跳校验白名单）
https://www.iesdouyin.com/share/video/7681631364923329842/     ← 302 跳板，别停这
   ↓
https://www.douyin.com/video/7681631364923329842              ← ★ 数据在这里（ld+json）
```

> 🔴🔴 **抖音发不了视频 —— 这是"试遍了"的结论，不是没试够**（2026-09-22 实测）：

| 试过的入口 / 接口 | 结果 |
|---|---|
| `iesdouyin` / `m.douyin` / `www.douyin` 分享页（4 种 UA） | 只有元信息，**零视频字段** |
| `www.douyin.com/light/{id}`（嵌入播放页，106 KB） | 只有 `dns-prefetch` 提示，**没有真地址** |
| `aweme/v1/web/aweme/detail`（4 组参数 × 2 UA） | 🔴 **HTTP 403 `Blocked by ArgusSecurityPlugin Uifid Not Found`** |
| `web/api/v2/aweme/iteminfo`（老接口，2 UA） | **HTTP 200 但正文长度 0** |
| `…/share/video/{id}/?is_share=1` | 302，无数据 |

**一共 11 种组合，一个 `.mp4` 都没有。**

**唯一能拿到视频的路**：逆向 `a_bogus` 签名 + 采集 `msToken` / `ttwid` cookie ——
那是**正面硬刚字节的反爬（Argus）**。不做，理由有三条：

1. **会一直坏**：签名算法平台想换就换，坏一次就得上线改一次
2. **有风险**：绕过反爬容易让**服务器 IP 被标记**，连带影响别的功能
3. **收益低**：为了"抖音也发视频"搭进一个长期维护负担，不值

> 所以抖音**只发卡片**。这是**已知限制，不是 bug**。
> 卡片信息（标题/作者/时长/点赞/封面）是**齐的**，点 🔗 就能去抖音看。

> ⚠️ 本质仍是普通 HTTP GET（**不是协议破解**），但"伪装爬虫"这件事
> 平台随时可能改策略。所以**解析失败时必须安静降级** —— 现在就是"解析不出来就当没看见这条消息"，不报错刷屏。

#### 16.3.3.1 抖音卡片里**有**什么、**没有**什么（2026-09-22 第二次实测）

用户反馈「抖音卡片没有播放和评论，发布时间」，逐个查清：

| 卡片上的字段 | 抖音 | 说明 |
|---|---|---|
| 标题 | ✅ | `VideoObject.name`（结尾自带「 - 抖音」，要剪掉） |
| 封面 | ✅ | `thumbnailUrl[0]`（被抖音裁成 **4:3**） |
| 作者 | ✅ | `creator.name` |
| 时长 | ✅ | `duration`（ISO8601，如 `PT0H13M4S`） |
| 点赞 | ✅ | `creator.interactionStatistic` → `LikeAction` |
| **评论** | ✅ | 🔴 **在顶层 `commentCount`**，**不在** `interactionStatistic` 里 —— 早期只扫了后者，所以「评论」一直没显示 |
| **发布时间** | ✅ | 🔴 `uploadDate` 是**坏值**：`"2026-09-05T17:00:00+08:00Z"`（有时区偏移了，末尾**还多一个 `Z`**）→ `new Date()` 得到 `Invalid Date` → 卡片那一行被**静默跳过**。已在 `fixIso()` 里统一容错 |
| **播放量** | ❌ **拿不到** | `VideoObject` 顶层**根本没有 `viewCount`**，`interactionStatistic` 里也只有 `LikeAction` / `FollowAction`。**是抖音的数据就不给**，不是我们没读到 |
| 粉丝数 | ❌ 不用 | `FollowAction` 有，但那是**作者总量**，放进卡片会误导，**故意不显示** |

> 💡 所以抖音卡片长这样：`标题 / 封面 / 作者·时长 / 发布 / 点赞·评论 / 🔗 打开`。
> **就少一个播放量** —— 这是我们唯一拿不到的字段。

#### 16.3.3.2 🔴「在抖音打开」不能指向 `www.douyin.com/video/{id}`

用户 2026-09-22 反馈：「点击在抖音打开会进入**抖音精选网页版**」。

**原因**：`www.douyin.com/video/{id}` 在**手机**上返回的是 **PC 版「抖音精选」网页**，
不是那个视频（实测手机 UA 请求该地址 → HTTP 200，不跳转，渲染的是 PC 版）。

**实测各个候选链接在手机上的行为**：

| 链接 | 手机上的结果 |
|---|---|
| `www.douyin.com/video/{id}` | ❌ PC 版「抖音精选」网页 |
| **`www.iesdouyin.com/share/video/{id}/`** | ✅ **手机 H5 视频页**（200，不跳转） |
| `m.douyin.com/share/video/{id}` | ✅ 同样是 H5 页（等价） |
| `www.douyin.com/discover?modal_id={id}` | ❌ 301 → `jingxuan?modal_id=`（还是精选） |
| `www.douyin.com/light/{id}` | ❌ 302 → `douyin.com/home` |

**所以卡片改用 `https://www.iesdouyin.com/share/video/{id}/`。**
⚠️ 在 PC 上它仍会 302 回 `www.douyin.com`，**没有损失**。


#### 16.3.4 快手 —— 数据藏在 HTML 里，要"挖"出来

**链路（⚠️ 短链会过 `chenzhongtech.com` 这个中转域，白名单里必须写它）**：

```
https://v.kuaishou.com/JJYSn5HT
   ↓
https://v.m.chenzhongtech.com/fw/photo/3x2qw55sgce69uq
   ↓
https://www.kuaishou.com/short-video/3x2qw55sgce69uq   ← 用**手机 UA** 抓这个页面（163 KB）
```

**数据在哪**：页面里有**一个没有变量名的 8.6 KB JSON 块**，作品数据全在里面。
拿不到变量名，只能这样定位：

```js
// ① 先找到 `"caption"` 的位置
// ② 再**往回找**一个能包住它的 `{`
// ③ 正向配平括号（要跳过字符串里的括号！），取最小的那个对象
```

> 🔴 **这是本模块最容易写错的地方**：
> "往前找**最近的** `{`" 是**错的** —— 那可能是个**已经闭合的兄弟对象**。
> 必须逐个往前试、**正向配平、取结束位置在 anchor 之后的那一个**。
> 自测第 19 组专门测了这个（`enclosingJson`），还测了"字符串里的转义引号不能打乱配平"。

**挖出来的字段**：`caption`（标题）/ `photoId` / `duration`（毫秒）/ `timestamp` /
`likeCount` / `viewCount` / `commentCount` / `userName` / `coverUrls` /
**`mainMvUrls`（视频直链！快手有）**。

> ✅ **快手可以直接下视频**（实测 2 MB，`HTTP 206` / `video/mp4`）。
> 代码优先选**非 hd** 那一档（hd 体积大，容易撞 30MB 上限）。
> 直链带签名（`pkey`），**有时效**，拿到就要立刻下。

### 16.4 安全设计（🔴 改动时不得绕过）

| 防线 | 做法 | 防什么 |
|---|---|---|
| **① 域名白名单** | 只抓 `cfg.policy.linkParse.hosts` 里的域（**根域写法，子域自动放行**） | **SSRF** —— 不然别人发个 `http://169.254.169.254/...` 就能让我们的服务器去读**云厂商的元数据服务**（里面有临时凭证） |
| **② 逐跳校验** | 短链跳转用 `redirect: 'manual'`，**每一跳**都单独查白名单 | 短链**能指向任何地方**。旧写法是"跟到底再检查最终地址"—— **太晚了**，请求已经发出去了 |
| **③ 只做模板拼接** | 抓回来的标题/简介**只往 Markdown 模板里填**，**绝不喂给模型** | **提示注入** —— 有人在视频标题里写「忽略你之前所有规则」，对卡片功能**完全无效** |
| **④ 平台开关** | `platforms: { github, bilibili, douyin, kuaishou }` 各自可关 | 某个平台开始抽风时，单独关掉它不用改代码 |

> 📌 **白名单是根域**：写 `douyin.com` 就自动放行 `v.douyin.com` / `www.iesdouyin.com` 不行（**不同根域得分开写**）。
> 短链的**每一个中转域**都要写进去，少一个就会在中间那跳被自己拦下：
> · 抖音：`douyin.com` + `iesdouyin.com`
> · 快手：`kuaishou.com` + **`chenzhongtech.com`**

### 16.5 限额 · 资源占用 · 会不会产生文件

> 这一节直接回答用户 2026-09-22 问的三个问题。

| 问题 | 答案 |
|---|---|
| **每天发的视频量有限制吗？** | 有，三层。① **同群冷却 3 秒** ② **全局每天 200 次解析**（`dailyLimit`）③ **QQ 平台**自己还有"今日发送文件容量上限"（错误码 `40093002`，**每天重置，官方没公布具体数值**）。实测当天传了 **71.2 MB** 都没撞到 |
| **对服务器有负荷吗？** | **几乎没有**。解析 = 一次 HTTP GET，几十毫秒。卡片渲染 = 字符串拼接。实测 **CPU 0%、内存常驻约 108 MB**。真正花时间的是视频（下载 + 上传），所以设了 `maxConcurrent: 1`（**一次只处理一个**）—— 2核2G / 3M 带宽，并发会把机器压垮 |
| **会不会产生文件？** | **不会**。视频全程以 `Buffer` 形式**放在内存里**，`data/` 目录只有 `budget.json` 和按天的事件日志（`events-YYYY-MM-DD.jsonl`）。所以**不需要定期清理临时文件** —— 需要清理的只有事件日志（见[第九章](#九日常运维)的轮换工具） |

> 💡 **一次视频全程实际耗时（2026-09-22 实测）**：
> B站 10 MB → 约 **37 秒**（下载 10.2s + 上传 24.8s，**上传是瓶颈**，服务器只有 3M 带宽）；
> 快手 2 MB → 约 **10 秒**。**这就是 `maxMB: 30` 别往上调的原因。**

## 十七、识图（图片 / 表情包）

> 用户需求（2026-09-22）：「群友希望能给 bot 增加识图功能，**不然发表情包他都看不懂**」
>
> 一句话：**群里的图片 / 表情包会被变成一句中文描述**，然后当成"这条消息说了什么"
> 接进正常的对话流程 —— 于是判断、回复、上下文记忆**全都自动看得见图片**。

### 17.1 🔑 最重要的一个结论：**不用换服务商**

一开始以为要接第三方视觉模型（智谱 `glm-4v-flash` 免费版 / 通义千问 VL），
那样就得**新增一个 API key、新增一个服务商** —— 而这恰好是自测第 18 组在防的事
（"跨服务商误配"，历史上真的出过：从智谱切到 DeepSeek 后降级链里还留着智谱的模型名，
一降级就 `HTTP 400 不支持的模型名`）。

**实际上完全不用**：

| 事实 | 来源 |
|---|---|
| **`deepseek-flash` 本身就支持图片输入** | [DeepSeek 官方《图像理解》](https://api-docs.deepseek.com/zh-cn/guides/vision) |
| 旧的 `deepseek-v4-flash-vision-exp`（2026-08-21 上线）**已下线**，请求由最新 Flash 承接 | 同上，文档原话 |
| 价格与 V4-Flash **一致**；一张图约 220 token（`detail:'low'` 缩到 512×512） | [发布公告](https://api-docs.deepseek.com/zh-cn/news/news260821/) |

> ✅ **结论：同一个 key、同一个 baseUrl、同一个模型名 `deepseek-flash`。**
> 零新增依赖、零新增凭证。
>
> 📌 所以 `policy.vision` 里**故意没有 `model` 字段** —— 它用 `ai.replyModel`。
> 少一个字段就少一处"跨服务商误配"的机会。自测第 20 组专门断言了
> `!('model' in cfg.policy.vision)`，防止以后有人"顺手"加一个。

### 17.2 QQ 是怎么把图片推给我们的

🔴 **`message_type` 是 `0`，不是 `1`** —— 这是最容易猜错的地方。
图片在 `attachments[]` 里：

```json
{
  "message_type": 0,
  "content": "",
  "attachments": [{
    "content_type": "image/gif",
    "filename": "120A6FDE0712FFBFC1C846B4C5DB192D.jpg",
    "width": 120, "height": 120, "size": 82933,
    "url": "https://multimedia.nt.qq.com.cn/download?appid=1407&fileid=...&rkey=..."
  }]
}
```

**线上历史事件统计**（2497 条事件，2026-09-14 ~ 09-22）：

| content_type | 出现次数 |
|---|---|
| `image/jpeg` | 131 |
| `image/gif` | **59**（表情包基本都是 GIF） |
| `image/png` | 19 |
| `video/mp4` | 5（**不做**，见 17.8） |
| `file` / `contact` | 各 3 / 1 |

> ⚠️ 加识图之前，这些消息**全被当成"空消息"扔掉了**
> （线上日志原样是 `不回（空消息）`）—— 所以群友发多少表情包，机器人都毫无反应。

### 17.3 那个图片地址（3 个必须知道的点）

```
https://multimedia.nt.qq.com.cn/download?appid=1407&fileid=...&rkey=...
```

| # | 事实 | 影响 |
|---|---|---|
| 1 | **裸 GET 就能下载** —— 实测不需要任何 header / UA / Referer | 不用装什么身份，直接 `fetch` |
| 2 | 长度约 **250 字符**（模型侧 URL 上限 8192） | 够用，但我们仍走 base64（见 17.4） |
| 3 | 🔴 **`rkey` 有时效** | **收到消息必须立刻下载**，不能排队 / 缓存 / "等一会儿再说"。社区里"图片地址过期"的报错就是这个（[AstrBot #1004](https://github.com/AstrBotDevs/AstrBot/issues/1004)） |

> 💡 所以我们**不走"把 URL 丢给模型让它自己下"**这条路 ——
> 虽然官方支持外部 URL（60 秒内下载完即可），但那样我们**控制不了时效和体积**。
> 自己下载 → 按字节判格式 → 卡大小上限 → 再 base64 内联，安全得多。

### 17.4 完整链路

```
群友发图片/表情包
   ↓
index.js  4.4 识图支路（在"提取文本"**之前**）
   ↓
vision.findImage(d)          ← attachments[] / msg_elements[] 里找第一张图
   ↓
vision.visionAllowed(scope)  ← 开关 / 静默 / 每日 300 张 / 同群 2 秒冷却
   ↓
vision.describe(img)
   ├─ qqmedia.downloadToBuffer   ← 复用现成的下载器，自带大小上限
   ├─ sniffMime(buf)             ← 按**字节**判真格式（filename 会骗人，见 17.5）
   └─ brain.describeImage(dataUrl)
        └─ callAI(...)           ← 复用重试/退避/降级链/预算/记账/超时
   ↓
d.__vision = "一只流泪猫吃面条，表情委屈…"
   ↓
brain.extractText(d) → "【图片】一只流泪猫吃面条，表情委屈…"
   ↓
L0 → L1 → L2（和普通文字消息完全一样）
```

#### 🔑 为什么挂在 `d.__vision` 上，而不是在每个调用点自己拼

`brain.extractText()` 是**唯一的文本出口** —— `hasUsableText` / `passHardRules` /
`isMentionOnly` / 上下文入栈 **全都走它**。

把描述挂在**消息对象**上、只改 `extractText` 这一处，
下游所有逻辑就自动"看得见"图片了。**少改一处就少一个漏改的坑。**

### 17.5 🔴 三个必须记住的坑

| # | 坑 | 说明 |
|---|---|---|
| 1 | **`filename` 的后缀会骗人** | 实测有个 `120A6FDE....jpg`，实际内容是 **GIF**（`content_type` 和 magic 都说是 GIF）。所以我们**按 magic 字节嗅探**（`ffd8ff`=JPEG / `89504e47`=PNG / `474946`=GIF / `RIFF....WEBP`=WebP），不信文件名。DeepSeek 本身也是按字节判的，所以能容错，但我们不该把 GIF 当 JPEG 报上去 |
| 2 | 🔴 **`@机器人 + 一张表情包` 会被判成"纯 @"** | 这种消息 `content` 只有 `<@openid>`、`mentions` 有 `is_you` —— 正好满足 `isMentionOnly` 的路径 B → 回一句固定的**「咋了」** → **图完全白看了**，用户还会以为识图没生效。修法：`isMentionOnly` 里"有识图结果就绝对不是纯 @" |
| 3 | **QQ 的表情标记会当正文喂给模型** | `<faceType=6,faceId="0",ext="...">` 是**给客户端渲染的协议字段**，对模型纯属噪音（一个表情包消息的 content 就只有这串东西）。加识图之前这类消息根本进不到模型，现在能进来了，所以顺手在 `stripAtMentions` 里清掉 |

### 17.6 成本与限流

| 项 | 值 |
|---|---|
| 单张成本 | **约 ¥0.0004**（in≈250 token + out≈33 token） |
| 单张耗时 | **0.7 ~ 5.0 秒**（120×120 的表情包 0.7s；2347×1080 的大图 5.0s） |
| 每日上限 | **300 张**（`policy.vision.dailyLimit`） |
| 同群冷却 | **2 秒**（`cooldownMs`） |
| 单图大小上限 | **8 MB**（base64 后约 11 MB，远低于请求体 48 MiB 上限） |
| 同一张图重复识别 | **0 元**（按内容 md5 去重，见 17.6.1） |
| 1000 张要多少钱 | 约 **¥0.4** |

> 🔴 **识图为什么要有自己一套限流**（不共用 `dailyCallLimit`）：
> 图片/表情包是**高频**消息（群里动不动连发一串），而 `dailyCallLimit(800)`
> 是留给"真的要回话"的。不隔离的话，**一波表情包就能把当天的聊天额度烧光**。
>
> ⚠️ 但识图的模型调用**仍然计入** `callCount` 和 `budget` ——
> 那不是重复限制，是**应该的**：钱是真的花了。

#### 17.6.1 🆕 同一张图只认一次（按内容 md5）

**实测数据（2026-09-22）**：

| 事实 | 数据 |
|---|---|
| QQ 的 `fileid` **每次都变** | 210 张图 → **210 个不同 fileid，重复率 0%**。**所以 fileid 不能用来去重** |
| 但按 `大小+尺寸` 看 | **重复率 28.6%** —— 群里"同一个表情包反复发"是常态，其中一个被发了 **21 次** |

做法：**用图片内容的 md5 做指纹**（我们本来就要把图下下来 base64，顺手算 md5 是零额外成本）。
命中缓存 → **一次模型调用都不发**，**也不占今日张数**（`markVision(scope, false)`）。

**线上实测**（同一张图连认三次）：

```
第一遍  下载 OK 1450KB · image/gif · 366×240
        [ai] in=250 out=15  → 描述："露西不屑冷笑抬手，表示'就这？'，无文字。"
        模型调用数 1764 → 1765（+1）
第二遍  命中缓存（同一张图之前认过，1450KB · 0 token）
        模型调用数 1765 → 1765（+0）
第三遍  命中缓存
        模型调用数 1765 → 1765（+0）
```

> 拿它的 URL 去下载直接 **HTTP 400**（rkey 过期）。
> **再次印证 17.3 第 3 条：图片必须"收到就下"**。


### 17.7 它**会不会**回你（重要，别误解）
识图 = **让它看得见**，**不是**"看到图就说话"。

| 场景 | 会回吗 |
|---|---|
| **@它 + 表情包** | ✅ **会**（而且认得图，不会只回"咋了"） |
| 主人发图 | ✅ 会 |
| 图 + 文字里有触发关键词 | ✅ 会 |
| **只发一张表情包，没 @ 也没关键词** | ❌ **不回**（描述会进上下文，但按"不抢答/省钱"的既有设计不发言） |

> 💡 **第 4 条为什么这么设计**：直接回表情包 = 群里每张图都要插一嘴，最招人烦，
> 也正是当初把 `sampleNonKeyword` 关成 0 的原因。
>
> ✅ 但描述**已经进了上下文**（30 条 / 10 分钟）——
> 所以**之后**有人问「刚才那个表情包啥意思」，它能答上来。
>
> 📌 如果你就是想让它看到图就吱一声，说一声，加个 `replyToImageOnly` 开关就行。

### 17.7.1 🔴 手机 QQ 发不出「@ + 带图」—— 怎么绕

**用户原话（2026-09-22）**：
> 「手机不太好发送@带图片，你有什么思路吗」

**症状**：用户在手机 QQ 里发了一张表情包，然后**引用那张图 + @机器人**，
结果机器人只回了一句**「咋了」**。线上日志原样是：

```
[群] GROUP_MESSAGE_CREATE | spaceyee: (无文本内容)
  ├ message_type=103 mentions=[{... "is_you":true ...}]
  └ 只有@没有内容 → 回固定应答
[send:group] ✓ 咋了
```

**根因**（真机数据，别猜）：

```
message_type = 103（引用消息）
content      = " <@机器人> "     ← **只有 @ 标记**
msg_elements = 空                ← 被引用的是图片，没有文字可给我们
attachments  = 无                ← ⚠️ 这次 QQ **没给**被引用的图片附件
message_scene.ext = ["ref_msg_idx=REFIDX_k3zt...", "msg_idx=REFIDX_nILq...", ...]
```

→ `extractText` 得到空串 → 被判成"只有@没内容" → 回固定应答。

**两条兜底（都做了）**：

| # | 机制 | 覆盖场景 | 可靠性 |
|---|---|---|---|
| ① | **`ref_msg_idx` → 描述缓存** | 有人引用**很久以前**的一张图 | ⚠️ 取决于 QQ 把那条被引用的消息推给过我们。实测 **346 条引用里 55 条能对上，其中 4 条是引用的图片** —— 能对上时 100% 准，对不上就查不到 |
| ② | **本群最近一张图（60 秒）** | **用户这次的实际操作**：先发图，紧接着 @ 它 | ✅ **实测精确命中这个案例**（图在 6 秒前） |

**机制①的实现**：每条消息的 `message_scene.ext` 里都有它自己的 `msg_idx`。
收到图时就把它自己的 `msg_idx` + 描述一起存下来；
之后有人引用它，`ref_msg_idx` 就是被引用那条的 `msg_idx` → 查回来。

> 💡 比"重新下载那张图"更好：**不用管 rkey 过期，也不重复花钱**
> （描述在收到图的那一刻就已经算好了）。

**机制②的实现**：`vision.recentImageDesc(scope, 60000)`。
⚠️ **只在"这句话除了 @ 它什么都没有"（`isMentionOnly`）时才用** ——
这种消息原本只会得到一句固定的「咋了」，所以拿图来回答**严格更好**。
只要 @ 它的同时还说了别的字，就完全不碰这个兜底。

> ⚠️ **顺序坑（先有鸡还是先有蛋）**：`isMentionOnly` 必须在设 `__vision` **之前**问 ——
> 设完之后它就不算纯 @ 了。写反了这个兜底永远不触发。

**回放验证**（用线上真实事件重跑，不是构造的）：

```

  msg_idx = REFIDX_7kFbiHTuQ6...
  描述 = 梗图：猫叼梨、背啤酒，配文"叼梨猫支啤"，谐音"刁梨猫支啤"，表达无厘头搞笑情绪。

【第二步】回放那条「引用图片 + @机器人」的消息
  message_type = 103 ｜ content = " <@...> " ｜ attachments = 0 个
  ref_msg_idx  = REFIDX_k3ztNcKNjE...
  ① 按 ref_msg_idx 查    → ❌ 没命中（QQ 没把我们引用的那条推给我们过）
  ② 按"本群最近一张图"查  → ✅ 命中
  最终采用: ✅ 梗图：猫叼梨、背啤酒…
  isMentionOnly → false（会真的回一句，不再回"咋了"）
```

**给群友的实操建议**（手机 QQ 上能用的三种）：

### 17.11 「刷图多了，上下文的 token 会不会跟着涨？」

> 用户 2026-09-22 的原话：
> **「那群里刷的图片多了，判断是否回复所需要的token不是也增加了？」**
>
> ✅ **他说得对，而且这是"条数+时效"两道闸拦不住的。**

#### 17.11.1 问题的本质

识图描述会被塞进**上下文记忆**（这样之后有人问「刚那图啥意思」它才答得上）。
而上下文是**每次 L1 判断 / L2 回复都要重发一遍**的：

```
群友发图 → 描述进上下文
              ↓
以后每一次 L1（判断要不要接话）都要带上它
以后每一次 L2（生成回复）也要带上它
```

🔴 **所以一条描述不是"花一次"，而是"它待在上下文里的这段时间内，每次调用都花一次"。**

#### 17.11.2 为什么"条数闸"拦不住 —— 实测数据

| 实测项 | 值 |
|---|---|
| 真实群聊消息长度 | 中位 **7 字**（平均 11.9，最长 617）|
| 识图描述长度 | 中位 **47 字**（平均 48.9，最长 92）|
| **中文 → token 换算比**（精确测的） | **1 字 ≈ 0.567 token** |

→ **一条识图描述 ≈ 7 条普通消息的体量。**
同样的"30 条"上限，实际大小能差 4 倍：

| 上下文内容 | 字数 | ≈token |
|---|---|---|
| 30 条普通短句 | ~330 字 | **187** |
| 30 条全是识图描述 | ~1680 字 | **953** |

#### 17.11.3 修法：补第三道闸 —— **长度**

```js
contextMsgMaxChars: 200,   // 单条太长就截断（防止一条 617 字的粘贴霸占上下文）
contextMaxChars: 800,      // 总长度上限，超了**从最旧的丢**
contextMinKeep: 5,         // 但至少留 5 条最近的
```

**量化效果**（用实测中位数模拟）：

| 场景 | 修前 | 修后 |
|---|---|---|
| 30 条普通短句 | 30 条 · 187 token | **30 条 · 187 token（一条不丢，完全不受影响）** |
| 30 条全是识图描述 | 953 token/次 | **454 token/次（省 499）** |
| 单条 617 字粘贴 | 617 字全塞进去 | **截断到 201 字** |
| 极端配置（总量上限 < 单条上限） | — | **仍至少留 5 条**（不会把上下文清空） |

> ✅ **两道闸的分工**：`contextMsgMaxChars` 防"一条超长霸屏"，
> `contextMaxChars` 防"一堆中等长度把总量撑爆"。

#### 17.11.4 代价是什么

**代价就是"记得少一点"** —— 图片/长文本多的时候，旧消息会被提前挤掉。

取值刻意留了余量：**正常聊天（30 条短句 ≈ 330 字）完全碰不到闸门**，
只有真的刷图或粘长文时才会开始丢旧的。要调就调 `contextMaxChars`。

#### 17.11.5 ✅ 顺手修掉的一个小浪费：当前这条消息被送了两遍

**现象**（线上真实打出来的 L1 提示词，一字不改）：

```
最近群聊：
小红: 今天好热啊
小明: 是啊 开空调了
小明: 这个表情包笑死我了        ← 作为"历史"

最新：小明: 这个表情包笑死我了   ← 作为"当前"

适合接话吗？
```

**为什么**：`index.js` 第 4 步会把当前这条推进上下文（**必须推** ——
否则后面几条消息就看不到它了，机器人会失忆）；
而 L1/L2 又把当前这条单独拼在「最新：」/「现在，XX 说：」里。
两边都没错，合起来就重复了。

**代价**：文本消息（7 字）每次回话多约 **12 token**；
**图片消息（描述 47 字）每次回话多约 58 token** —— 而且这是**每次回话都发生**。

**修法**：新增 `brain.contextText(scope, msg)` ——
拼上下文时把**当前这条按 `msgId` 精确挑出去**。

```js
function contextText(scope, msg) {
  const cur = msg?.id || '';
  return recentContext(scope)
    .filter((m) => !(cur && m.msgId === cur))     // ← 就这一行
    .map((m) => `${m.name}: ${m.content}`)
    .join('\n');
}
```

**修完后**（同一个探针，一字不改地再打一遍）：

```
最近群聊：
小红: 今天好热啊
小明: 是啊 开空调了

最新：小明: 这个表情包笑死我了

适合接话吗？
```

> ⚠️ **两个"看起来更简单"的错法，都别用**：
>
> | 错法 | 为什么错 |
> |---|---|
> | 干脆**不把当前消息推进上下文** | 后面几条消息就看不到它了 —— 机器人会**失忆**（"他刚才说了啥？"） |
> | **内容相同就跳过** | 群里连着发两条「哈哈哈」是常态，会被**误伤**。必须用 `msgId` 精确匹配 |
>
> 而且**没有 msgId 的消息**（老数据、机器人自己的发言）不做剔除 —— 宁可不省，不可误删。

### 18.5 2026-09-21 的改动（线上排查后）

> **起因**：机器人跑到 **16:47 突然不回复**，日志显示"限额"，但话费并没超。

| # | 改动 | 为什么 |
|---|---|---|
| **1** | `policy.dailyCallLimit` **300 → 800** | 撞的是**调用次数**上限，**不是钱**。实测 300 次只花 ¥0.86，而 ¥3 预算能撑约 1000 次 —— 次数限制比钱限制**早 3 倍刹车**。历史上最高才 300，800 给足了余量 |
| **2** | 新增 `policy.quietHoursEnabled: false` —— **关掉深夜静默** | 用户判定：半夜本来也没几个人，静默反而让偶尔来的人以为"它坏了"。`quietHours: [2,7]` 保留着，**改回 `true` 就恢复** |
| **3** | `budget.js`：未登记模型**不再"不记账"** | 旧逻辑是 `priceOf()` 查不到就 `return`，**一分钱都不记** → 换个没登记的新模型 = 「钱的上限」彻底失效 = 无限花。现在按**最贵的已知价**（`[9,27]`）保守计费 |
| **4** | `brain.js` 日志文案：`今日调用额度已用完` → **`今日调用次数已用完（N/800 次；这是次数上限，跟话费无关）`** | 旧文案里的"额度"指的是**次数**，但极易被读成"话费" —— 那天就是因此白排查了半天 |

**连带更新**：本章 17.2 的数字、6.4「刹车」清单、配置速查表、排错表的「不回原因」都已同步。

> ⚠️ **一个留下的坑（现在不触发，将来会）**：
> 静默时段那条分支（**"纯 @ 回一句咋了"**）当初就**没有静默检查** ——
> 所以静默开着的时候，凌晨 3 点只发一个 `@它`（不带字），它**仍会回"咋了"**。
